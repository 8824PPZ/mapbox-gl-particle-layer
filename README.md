# mapbox-gl-particle-layer

GPU wind & flow particles for **[Mapbox GL JS](https://github.com/mapbox/mapbox-gl-js)** and
**[MapLibre GL JS](https://github.com/maplibre/maplibre-gl-js)** — one `CustomLayerInterface`,
no dependencies, ~11 kB gzipped.

Particles are advected by a wind raster entirely on the GPU: positions live in a ping-ponged
RGBA8 texture, the update pass is a fragment shader, and nothing is ever read back to the CPU.

```
npm install mapbox-gl-particle-layer
```

## Features

- **Pure custom layer** — works in Mapbox GL JS ≥ 2.15 and MapLibre GL JS ≥ 3, no forks, no monkey patching.
- **GPU simulation** — FBO ping-pong, 16-bit positions packed into two 8-bit channels, so it runs on every WebGL1 device.
- **Speed → color** — velocity is sampled in the vertex shader and looked up in a 1D ramp texture; five presets or your own stops.
- **Drop rate** — speed-dependent respawn keeps the field evenly seeded instead of draining at convergence zones.
- **Optional trails** — one extra full-canvas framebuffer, `fadeOpacity < 1`.
- **Viewport constrained respawn** — useful at city zoom, where most of a global field is off screen.
- **Runtime API** — swap the wind field, the ramp, the particle count or the density without re-adding the layer.

## Quick start

### MapLibre GL JS

```js
import maplibregl from 'maplibre-gl';
import 'maplibre-gl/dist/maplibre-gl.css';
import { ParticleLayer } from 'mapbox-gl-particle-layer';

const map = new maplibregl.Map({
  container: 'map',
  style: 'https://demotiles.maplibre.org/style.json',
  center: [8, 34],
  zoom: 2.2,
});

const layer = new ParticleLayer({
  id: 'wind',
  windSource: '/wind-global.png',
  windBounds: [-180, -85, 180, 85],
  maxWindSpeed: 30,
  numParticles: 32768,
});

map.on('load', () => map.addLayer(layer));
```

### Mapbox GL JS

```js
import mapboxgl from 'mapbox-gl';
import 'mapbox-gl/dist/mapbox-gl.css';
import { ParticleLayer } from 'mapbox-gl-particle-layer';

mapboxgl.accessToken = '…';

const map = new mapboxgl.Map({ container: 'map', style: 'mapbox://styles/mapbox/light-v11' });

map.on('load', () => {
  map.addLayer(new ParticleLayer({ id: 'wind', windSource: '/wind-global.png' }));
});
```

The layer is added like any other layer, so re-adding it after `map.setStyle()` behaves as you
would expect.

## Wind data

`windSource` accepts a URL, an `ImageBitmap`/`HTMLImageElement`/`HTMLCanvasElement`, or raw
RGBA bytes (`{ width, height, data }`).

The image is read as an **equirectangular raster** (row 0 = north) where the red and green
channels carry the two velocity components:

| channel | meaning | decoding |
| --- | --- | --- |
| `r` | east–west component `u` | `(r / 255 * 2 - 1) * maxWindSpeed` |
| `g` | north–south component `v` | `(g / 255 * 2 - 1) * maxWindSpeed` |
| `b`, `a` | unused | — |

`128` means calm, `0`/`255` mean `∓maxWindSpeed` m/s. This is the layout used by most public
wind rasters (GFS/ECMWF tiles, `webgl-wind`, `mapbox-exif-layer`), so existing images usually
work as-is. Bounds are not stored in the image: pass them with `windBounds`
(`[west, south, east, north]`, default = whole world). Images loaded from another origin need
CORS headers, otherwise the texture upload fails.

This repository ships `public/wind-global.png`, a synthetic 720×360 global field generated by
`npm run wind` (`scripts/generate-wind.mjs`) — handy as a placeholder until you plug in real
data.

## Options

| option | type | default | description |
| --- | --- | --- | --- |
| `id` | `string` | — | **required**, layer id |
| `windSource` | `string \| TexImageSource \| RawWindData` | — | wind raster; may be set later via `setWindSource()` |
| `windBounds` | `[w, s, e, n]` | `[-180, -89.9, 180, 89.9]` | geographic bounds of the raster |
| `maxWindSpeed` | `number` | `30` | m/s at a saturated channel (decode scale) |
| `colorScale` | `number` | `= maxWindSpeed` | m/s mapped to the end of the ramp |
| `numParticles` | `number` | `16384` | rounded up to the next perfect square (square texture) |
| `dropRate` | `number` | `0.003` | base respawn probability per frame at 60 fps |
| `dropRateBump` | `number` | `0.006` | extra respawn probability, proportional to speed |
| `timeScale` | `number` | `45000` | simulated seconds per real second (the "fast forward" factor) |
| `speedFactor` | `number` | `1` | multiplier on top of `timeScale` |
| `colorRamp` | `stops \| preset` | `'wind'` | `[[stop, color], …]` or `wind`/`viridis`/`plasma`/`thermal`/`mono` |
| `particleSize` | `number` | `2.2` | dot diameter in CSS pixels |
| `opacity` | `number` | `1` | global alpha |
| `fadeOpacity` | `number` | `1` | `1` = no trails, `0.9` = long comet tail |
| `constrainToViewport` | `boolean` | `false` | respawn inside the current viewport |
| `animate` | `boolean` | `true` | auto `triggerRepaint()` every frame |
| `maxFPS` | `number` | `0` | cap the simulation step rate, `0` = uncapped |
| `wrapLongitude` | `boolean` | `true` | let particles cross the antimeridian |
| `mapRuntime` | `'mapbox' \| 'maplibre'` | — | informational hint only |

## Instance API

```js
layer.setWindSource(urlOrBitmap, bounds?);   // swap the field at runtime
layer.setColorRamp('plasma');                // preset name or stops
layer.setNumParticles(65536);                // rebuilds the state textures
layer.updateOptions({ particleSize: 3, fadeOpacity: 0.92 });
layer.restart();                             // reseed all particles
layer.start();                               // resume animation
layer.stop();                                // freeze (last frame stays)
layer.remove();                              // map.removeLayer(id)
layer.ready;                                 // true once the raster is uploaded
layer.particleCount;                         // effective (rounded) count
```

## How it works

```
wind.png ──► WindTexture ──┐
                           │
particle state (RGBA8) ──► update pass ──► draw pass ──► canvas
        ▲                    │  advect        │  point sprite
        └────────────────────┘  drop/respawn  │  speed → ramp
                                              └─► (optional) trail buffer
```

1. **State** — every particle is one texel of a square RGBA8 texture. `x` is packed into
   `(r, b)` and `y` into `(g, a)` as high/low bytes, giving 1/65025 of the field domain of
   precision (~0.006° for a global raster) inside a format that is renderable everywhere.
2. **Update pass** — a full-screen quad writes into the spare texture. Each fragment decodes its
   position, samples the wind with manual bilinear filtering, converts m/s to degrees (accounting
   for the latitude-dependent metres-per-degree), and applies the respawn probability
   `1 - exp(-rate * dt)`. Fast particles drop sooner (`dropRateBump`), which keeps the field from
   piling up where the wind converges.
3. **Draw pass** — one `gl.POINTS` vertex per particle reads the state texture, projects the
   position through the custom layer matrix, samples the wind again for the velocity, and picks
   a color from the ramp. The fragment shader only does the round mask.
4. **Trails** — when `fadeOpacity < 1`, particles are composited additively into a full-canvas
   framebuffer that is multiplied by `fadeOpacity` every frame and blitted on top at the end.

## Performance

- The simulation cost scales with `numParticles`, the draw cost with coverage (particles × size).
  16k particles at size 2.2 is comfortable on integrated graphics; 65k–130k wants a discrete GPU
  or a small viewport.
- `maxFPS` decouples the simulation rate from the render rate — a good first knob on battery.
- `constrainToViewport` does not reduce the work, but it makes zoomed-in views look dense with
  far fewer particles (`4096` particles constrained to a city beats `65536` spread over the globe).
- Turn off `animate` and call `layer.restart()`/`triggerRepaint()` yourself for a
  "render on demand" map.
- Particle textures are square: `numParticles: 16384` → 128×128 (exact), `20000` → 143×143
  (20449 particles).

## Compared to Mapbox's `raster-particle`

`raster-particle` is a style layer: it is fed by a Mapbox-hosted source, its parameters live in
the style JSON, and it is tied to Mapbox's release cycle. This layer is a plain npm package:
bring your own raster (a URL, a canvas, raw bytes), drive it from JS at runtime, and use the same
code on MapLibre. The trade-off is that you own the data pipeline and the styling.

## Development

```bash
npm install
npm run dev        # demos at http://localhost:5173
npm run wind       # regenerate public/wind-global.png
npm run typecheck  # tsc --noEmit, includes the Mapbox/MapLibre compatibility test
npm test           # vitest (utils + option resolution)
npm run build      # ESM + CJS + .d.ts into dist/
npm run lint
```

```
src/
├── index.ts                 # public entry
├── ParticleLayer.ts         # CustomLayerInterface implementation
├── types.ts                 # structural types (no runtime imports)
├── core/
│   ├── ParticleSimulator.ts # programs, ping-pong FBOs, draw/trail passes
│   ├── WindTexture.ts       # raster upload + URL loading
│   └── gl.ts                # program/texture helpers
├── shaders/                 # GLSL, inlined at build time (`#include "common.glsl"`)
└── utils/                   # math, color ramps, 16-bit packing, PRNG
demos/                       # Vite demos: maplibre, mapbox, color-ramp, viewport-constrained
```

Shaders live in `src/shaders` as separate files and are inlined by a ~30 line Vite plugin
(`vite.config.ts`), so the published bundle contains no runtime file loading and works with any
bundler. If you want to change the motion, `update.frag.glsl` is the only file you need to touch;
if you want to change the look, `draw.vert.glsl` (color) and `draw.frag.glsl` (shape) are the
places to go.

Releases are cut by pushing a `v*` tag — `.github/workflows/release.yml` publishes to npm and
creates the GitHub release.
